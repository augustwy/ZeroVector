# ZeroVector 代码审查与重构报告

- **审查日期**：2026-10-22
- **范围**：`zerovector-core` 全部实现、`zerovector-spring-boot-starter`、`zerovector-spring-boot-example`、Maven 构建
- **结论**：原实现的主要问题不是零散写法，而是**两条主链路没有真正闭合**：mmap 正文存储没有接入上传/导航；语义树“原子保存”实际上会覆盖旧文件。此次按“正确性优先、删除无效抽象”的原则做了结构性重构，而非局部补丁。

---

## 一、最严重的问题（已修复）

### 1. mmap 存储在重启后从 offset 0 覆盖旧数据

**位置**：`MMapDocumentStore.open()`

原实现 `open()` 映射文件后 `MappedByteBuffer.position()` 恒为 0；`addChunk()` 直接用当前 position 追加。重启后新增文档会覆盖文件开头，旧索引仍指向被覆盖的字节——**静默数据损坏**，而测试只验证了“重启后读取”，没有验证“重启后追加”。

**修复**：

- 打开时根据索引计算 `usedBytes`，把写入位置恢复到索引末尾；
- 校验 `used <= fileSize`，索引越界直接报 `INDEX_CORRUPT`，不再静默扩文件；
- 新增 `indexPersists_acrossCloseReopen` 用例，重启后追加并同时校验新旧内容。

### 2. 语义树保存并非原子，旧数据会被提前覆盖

**位置**：`ShardedTreeStorage.saveTree()`

原实现先覆盖固定文件名的 `node_0.json` / `chunk_0.json` / `root.json`，最后才写 `metadata.json`。所谓“metadata 作为提交点”并不成立：崩溃时旧 metadata 指向的分片已经被新内容覆盖，得到的是混合数据集。

**修复**：

- 每次保存写入**全新 generation** 的文件名（`node_<gen>_<i>.json` 等）；
- 全部写完后原子替换 `metadata.json`；
- 提交成功后删除旧 generation；
- 启动时清理未提交的孤儿 generation；
- 读路径加读锁、提交短暂加写锁，保存过程中查询仍读取完整旧数据集。

### 3. 正文存储没有接入主流程，且查询阶段错误地加载全文

**位置**：`SemanticTreeManager`、`DocumentChunk`、`HybridNavigator`、`LocalFileChunkStorage`

原实现 `SemanticTreeManager` 从未调用 `chunkStorage.saveChunk(s)`；`DocumentChunk` 保存文件路径，导航时用 `Files.readString` 整文件读取。`MMapDocumentStore` 只在单元测试里被使用，README 宣称的 mmap 零拷贝与实际运行路径无关；文件路径/分片元数据还在树和 `ChunkStorage` 之间重复。

这里的设计意图是合理的：**大文件只保留路径，导航只读摘要，回答才读原文**。原实现的错误不是“存路径”本身，而是路径没有统一生命周期、查询阶段整文件读取、content-based 分片重启后不可读。

**修复（架构调整）**：

- 新增 `DocumentChunker`：默认 `ChunkingPolicy.AUTO`，小文档整篇作为一个单位；只有超过 `chapterSplitThresholdChars`（默认 100000）才按 Markdown/中文章节标题或段落长度切片；
- 大文档在树中是 `NodeType.DOCUMENT` 节点，子节点是章节叶子；小文档直接是 `LEAF`，回答拿到整篇原文；
- 新增 `DocumentSourceStore`：
  - `SourceMode.COPY`（默认）：把解码正文写成 UTF-8 托管副本，与用户原文件修改隔离；
  - `SourceMode.REFERENCE`：只保存原文件绝对路径；
  - 按 `sourceOffset/sourceLength` **按需读取章节原文**，不整篇读入；
- 文件上传改为**流式切片**：`StreamingDocumentChunker` 按行解码、边写 COPY 副本边累计字节区间，只保留章节
  元数据；章节理解时再逐节读取（COPY/REFERENCE/INLINE 均支持），避免大文件同时驻留完整正文和所有章节字符串；
- `DocumentChunk` 支持 `content`（接口直传小文档，写 `ChunkStorage`/mmap）和 `source`（章节源文件引用）两种形态；
- 语义树只保存 `DocumentChunk.metadataOnly()`（摘要、MD5、源区间、章节元数据）；
- `HybridNavigator` 不再依赖 `ChunkStorage`，导航结果只含摘要，不读正文；
- `SearchResult.getChunkContent` / `toDocumentText` 在回答阶段才调用 `SemanticTreeManager.readChunkContent`；
- 查询接口不再把全文序列化进响应。

### 4. 文档理解提示词把当前块发送了两次

**位置**：`DocumentComprehender.buildContext()` + `comprehendChunkWithLLM()`

`buildContext()` 已包含“当前内容：<chunk>”，调用方又在末尾拼接了一次 `chunk`。每次理解都重复发送整块正文，直接翻倍 token 成本，并可能干扰模型。

**修复**：上下文只保留“前文摘要/前文关键词”，当前块单独拼接；`LLMPromptTemplates.comprehendChunk` 显式接收 `(context, chunk, index, total)`。

### 5. 批量上传结果与文件下标错位

**位置**：`DocumentController.uploadDocuments()`（example）

控制器按原始 `files[i]` 输出结果，但 `addDocuments` 会跳过空文件；一旦中间有空文件，后续文件名与结果全部错位。

**修复**：只把非空文件加入 `accepted` 列表，结果与 `accepted` 严格对齐；同时修复上传路径穿越（取 `getFileName()`）、同名覆盖（UUID 前缀）与临时文件清理。`finally` 只清理 COPY 模式的临时文件；REFERENCE 模式必须保留上传文件，否则重启后无法读取原文。

## 二、树构建与导航的正确性问题（已修复）

| # | 问题 | 修复 |
|---|------|------|
| 1 | `buildLargeDocumentSet` 在“所有文档被聚成 1 类”时递归调用自身，可无限递归直到 `StackOverflowError` | 单类别直接退化为叶子；增加 `MAX_DEPTH=8` 深度上限 |
| 2 | `updateTree` 用 `newResults.get(i)` 与 `chunkEntries.get(i)` 按下标配对，依赖 Map 迭代顺序 | 改为按 `docId` 关联；新增文档找不到结果时跳过并告警 |
| 3 | 聚类结果漏文档时静默丢失 | 记录已分配集合，漏掉的文档各自成类 |
| 4 | 默认分类在文档数不能被 3 整除时丢弃尾部文档 | 用 `base + remainder` 分配 |
| 5 | 分类节点的 `cat.nodeId` 被随机生成后从未进入树，关键词索引指向不存在的节点 | 递归时显式传入 rootId，分类节点与索引使用同一个 ID |
| 6 | 叶子拆分时丢失原文档的关键词/实体/示例问题 | 保留原叶子元数据，并把原关键词重新映射到新叶子 |
| 7 | 导航提示词过滤了空子节点，但解析时按未过滤列表取下标，索引可能错位 | 提示词与解析共用同一个 `List<TreeNode>` |
| 8 | 关键词同分时父类目（聚合了子节点关键词）可能抢走精确命中，导航从父类目开始并选错分支 | 同分时优先叶子节点；兜底候选也按“分数 + 叶子优先”排序 |
| 9 | LLM 返回 `LLMResponse.failure` 后仍继续解析空内容 | 所有调用点检查 `success()`；导航决策失败时降级到关键词兜底，解析失败才抛异常 |
| 10 | 导航出现环（A→B→A）时可能死循环 | 记录已访问节点，重复即兜底 |
| 11 | `Stop` 分支构造结果后没有返回，继续走 hook 和循环 | 显式 `return` |
| 12 | 文档级 `docId` 已改 UUID，但关键词定义仍写 `doc_ + System.currentTimeMillis()` | 传入真实文档 ID；`KeywordDefinition` 允许 definition/context 缺失，避免整篇失败 |
| 13 | 聚类/元数据提取的某个 LLM 调用抛异常会让整次入库失败 | 聚类异常回退默认分类；节点元数据异常返回空列表 |
| 14 | 分片树保存时 `new HashMap<>(tree.nodes())` 会加载全部懒节点 | 这是保存语义决定的；查询路径仍保持懒加载，只物化写入快照 |

## 三、存储、缓存与并发的其他修复

### 存储

- `MMapDocumentStore` 全面改用 **JDK 25 FFM**（`Arena` / `MemorySegment`）：
  - 原 `MmapUtils` 通过反射访问 `MappedByteBuffer.cleaner`，在 JDK 25 默认模块封装下**静默失败**，Windows 文件锁无法释放，`compact()` 实际不可用（原测试直接 `@Disabled`）。
  - 现在关闭 `Arena` 即确定性解除映射；`compact()` 两个 Windows 用例已重新启用并通过。
- `open()` 增加数据文件 >2GB、索引越界、长度不匹配校验；`getChunk` 不再可能因损坏索引分配超大数组。
- `compact()` 先解除旧映射再移动/替换文件，失败时从备份恢复；数据文件写入后 `force`。
- `clear()` 先解除映射再截断，避免 Windows 上截断被映射文件失败。
- 索引文件改为带版本头的 `Base64(chunkId)\toffset\tlength`，原子替换，避免 chunkId 含逗号时解析错位；删除 `abs(hash)` 越界问题（已有 `floorMod`）。
- `ShardedTreeStorage` 读路径读锁覆盖“索引定位 + 分片读取”，避免保存提交后删除旧文件与正在读取旧分片的查询竞争。
- `SemanticTree.saveToFile` 改临时文件 + 原子移动。
- `KeywordDictionary` 保存改原子写；加载改为类型化 `Snapshot`，不再裸 `Map` 强转；大小写/空白统一 `Locale.ROOT` 归一化；权重改为取最大值，避免重复更新树导致权重无限累加。

### 缓存

- 删除 Spring AI / LangChain4j Provider 内部的第二层 summary 缓存——与 `CachedLLMProvider` 重复，且缓存命中返回 0 token 会污染统计。
- 缓存值改为 `(response, prompt)` 一起保存，避免 prompt 缓存单独淘汰后相似匹配失效；相似命中时写入当前 prompt，而不是复用旧 prompt。
- 只缓存成功响应；Caffeine `get(key, loader)` 提供单飞加载，避免并发击穿。
- 新增 `ANSWER_QUESTION` 请求类型并默认禁用缓存：最终问答与完整上下文强相关，不应复用摘要缓存。
- 删除 `CacheConfig.prefix`（从未使用）。

### 并发与生命周期

- `SemanticTreeManager` 不再要求调用 `initialize()`：构造时完成存储初始化与已有树加载，失败立即抛出。
- 写操作统一由 `ReentrantLock` 串行化；读操作读取 `volatile NavigationState(tree, navigator)` 不可变快照，构建期间不会看到半成品树。
- `HybridNavigator` 彻底无状态；导航历史/当前节点/已访问集合全部是方法局部变量。
- `addDocuments` 改为一次理解、一次建树、一次落盘，而不是逐文档全量重写树。
- `SemanticTreeManager.close()` 先等待执行器任务结束，再关闭存储；构造失败也会关闭已打开的资源。
- `SemanticTreeManager` 的公共异步上传改用独立虚拟线程执行器：原实现把整次上传跑在带信号量的 `executor` 上，`maxConcurrentRequests=1` 时外层任务占用唯一许可、内层分块理解任务永远拿不到许可，形成死锁。已新增 `asyncUploadWithSingleConcurrencyPermit_doesNotDeadlock` 回归用例。
- `TreeBuilder` 不再自建 ExecutorService（原实现每次建树创建一个且从不关闭）。
- `LLMExecutors` 删除 RPS 限流，只保留并发度信号量；全局速率统一由 `RateLimitedLLMProvider` 负责，避免两套节拍叠加。
- `RateLimitedLLMProvider` 增加参数校验，修复 `maxRequests<=0` 时 `getFirst()` 抛异常的问题。

### 配置与 Spring 集成

- `zerovector.use-sharded-storage` / `shard-size` 原来被绑定但**从未传给 `SemanticTreeManager`**（KnowledgeBaseManager 硬编码 `true`）；现已贯通。
- `max-chunk-tokens` 实际按**字符**使用，重命名为 `max-chunk-chars`，删除未使用的 `chunk-overlap-tokens`。
- 删除 `zerovector.concurrency.requests-per-second`（与 `rate-limit` 重复）。
- `SemanticHub` 去掉 `@Component`（它同时由自动配置注册）；所有依赖改为构造器注入。
- 自动配置的 LLM 选择不再靠 `@ConditionalOnBean(ChatModel)` 的注册顺序；改为在创建缓存提供者时按 Bean 名解析：
  - 优先用户自定义 `LLMProvider`；
  - 其次 Spring AI；
  - 再次 LangChain4j；
  - 多个用户 Bean 时要求 `@Primary`，否则给出明确错误。
- `DocumentComprehender` / `KnowledgeBaseManager` 通过 `@Qualifier("zeroVectorLLMProvider")` 注入，避免与原始适配器 Bean 歧义。
- 知识库目录增加 `.zerovector-kb` 标记，修复“新建但尚未上传文档的知识库重启后消失”的问题。
- `KnowledgeBaseManager` 资源泄漏修复：`Files.list`/`Files.walk` 全部 try-with-resources；`currentKnowledgeBase` 改 `volatile`；创建/删除/切换同步化。

## 七、仍建议后续处理（本次未做）

1. **文档删除/更新 API**：目前只有“追加 + MD5 去重”，没有删除单文档并同步清理树节点、倒排索引、mmap 数据的入口。需要设计 `deleteDocument(docId)`，并处理树节点合并/回缩。
2. **关键词包含匹配是 O(词典大小)**：中文兜底路径每次查询扫描全部关键词。数据量大时应换 Aho-Corasick 或双字/三元组索引。
3. **mmap 索引每篇文档写一次全量索引**：`SemanticTreeManager.saveTree` 会 `flush` 所有分片索引。文档量很大时可改为增量日志 + 周期 checkpoint。
4. **单分片 2GB 上限**：已用 4 分片规避，但超大数据集仍需要动态分片或按大小再分片。
5. **缓存相似匹配仍是线性扫描**（默认只在 4 种确定性提取类型上启用，最多 100 条）。可换 SimHash/MinHash 预筛。
6. **PDF/Word 转换器质量**：目前是启发式字体/样式识别，复杂版式（多栏、表格跨页）效果有限；建议换成专门的文档解析服务或在示例中明确限制。
7. **没有鉴权/配额/多租户隔离**：示例 REST API 直接暴露上传、缓存清理、知识库删除，仅适合本地演示。
8. **没有目录 fsync**：文件内容与 metadata 使用原子 rename，但极端掉电情况下目录项仍可能未持久化；对强持久化要求可增加目录 `fsync`。
9. **LLM 调用成本**：建树对每个类目做 3 次元数据提取，文档多时调用量较大；可合并为一次结构化提取，或对类目名/关键词做批量请求。
10. **错误分级 `ErrorLevel`**：异常体系保留但所有抛出点恒为 `ERROR`，要么补齐 WARN/INFO 语义，要么删除该维度。

## 八、破坏性变更清单

- `SemanticTreeManager` 构造即初始化，删除 `initialize()`。
- `DocumentChunk` 改为章节级：支持 `content` 内联正文，或 `source` + `sourceOffset/sourceLength/sourceCharset` 源文件区间；旧的 `filePath` 平面字段被替换。
- 新增 `SourceMode`（`COPY` / `REFERENCE` / `INLINE`）与 `DocumentSourceStore`；删除旧 `DocumentCopyStorage`、`DocumentCopyInfo`、`DocumentCopyStorageConfig`。
- 新增章节切片：`DocumentChunker` 默认 AUTO，小文档整篇；大文档按 Markdown/中文章节标题或段落切分，并生成 `NodeType.DOCUMENT` + 章节叶子。
- `HybridNavigator` 不再接收 `ChunkStorage`，导航结果只含元数据。
- `ChunkStorage` 语义收窄为“接口直传/INLINE 正文存储”，大文件原文由 `DocumentSourceStore` 负责。
- `ZeroVectorProperties.LLMContext` 新增 `chapterSplitThresholdChars`（默认 100000）。
- `DictionaryStorage` 改为 `load()` / `save(KeywordDictionary)`。
